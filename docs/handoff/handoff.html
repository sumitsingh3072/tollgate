Tollgate

Every token pays the toll. A self-hostable, OpenAI-compatible gateway that sits between applications and AI models. It controls who may use the models and how much, avoids paying twice for the same work, shares capacity fairly, and shows exactly what is happening.

This document explains the whole system in plain language: what it does, how a request moves through it, how each feature works, how to run and operate it, and where everything lives in the code.

1. What Tollgate is, in one page

Think of a toll gate on a road. Every car (a request from an app) passes through it. The gate checks the car is allowed (an API key), makes sure it hasn't used the road too much today (limits and quotas), waves through cars it already knows the answer for (the cache), lets cars going to exactly the same place travel together (coalescing), and lets cars onto a narrow bridge in a fair order (the fair queue). Behind the gate is the road itself: an AI model.

Applications don't need to change. Tollgate speaks the same language as OpenAI's API, so an app only changes one setting, its base_url, from OpenAI's address to Tollgate's. Everything else (the SDK, the code) stays the same.

What makes it different
  • A cache that doesn't bloat. It stores an answer only when the same question comes back, so one-off questions never fill it up.
  • Request coalescing. If 50 identical questions arrive together, the model is asked once and all 50 get the answer.
  • Fair queuing. When the model is busy, the person who has received the least service goes next, so one heavy script can't make everyone wait.
  • Proof. Metrics, logs and dashboard pages show each of these working, and benchmarks measure them.

It runs with one command (docker compose up -d). By default the models come from Google's Gemini API, so the machine running Tollgate stays light; switching to fully local models with Ollama is one setting.

4. The life of a request

When an app sends a question, it passes through seven steps. Each step can finish the request early, which is what keeps the model from doing unnecessary work.

  1. Auth. The key is hashed and looked up in Redis (it falls back to the database only on a miss, and the result is remembered for 60 seconds). Unknown or revoked keys get a 401.
  2. Limits. Two counters in one Redis round trip: requests this minute and tokens today. Over either: 429 with a Retry-After header saying when to try again.
  3. Cache lookup. If the request is deterministic (temperature 0) and the same request was answered before, the stored answer is returned in milliseconds.
  4. Coalescing. If an identical request is being answered right now, this one joins it instead of asking the model again.
  5. Fair queue. Only genuinely new work gets here. It waits for one of the model's slots; the fairest request goes next.
  6. Model call. The request goes to the model. If that model fails, is overloaded or is too slow, the next model in the alias answers instead.
  7. After the response. Tokens are billed to the key, the answer may be cached, and a log entry is queued.

Every response carries headers that tell the caller what happened: which model answered, whether it came from cache, whether it was shared, how long it waited, and how much of the limit is left.

5. Features, explained

5.1 API keys

Keys look like tg_live_ followed by 32 random characters. The full key is shown once, when it is created; only a fingerprint (a SHA-256 hash) is stored, so even someone reading the database cannot use the keys. Revoking a key takes effect immediately. Each key has its own requests-per-minute limit and daily token budget.

5.2 Model aliases and fallback

Apps ask for an alias, not a specific model. Each alias is a short list of models tried in order:

Gateway-side waiting (a full queue) is never counted as the model failing, so a busy period can't take a healthy model offline.

5.3 The cache that doesn't bloat

Most questions are only ever asked once. A cache that stores everything fills up with them and throws out the answers people actually reuse. Tollgate uses six layers of defense:

  1. Only deterministic, complete answers are considered: temperature 0, the model finished normally, no tool calls, and under 16 KB.
  2. A precise key: the question is normalized (extra spaces removed) and combined with the alias and the caller's key, so different callers never share entries by accident.
  3. Admission on second sight: the first time a question is seen, only a tiny marker is kept. The answer is stored the second time.
  4. A separate, capped memory: answers live in their own Redis that evicts the least-frequently-used entries, so cache pressure can never wipe out rate-limit counters.
  5. Scopes: private per key by default; a shared pool (the faq alias) is opt-in, with a per-key limit on how many new entries each key may add per minute.
  6. Expiry: entries expire after 24 hours.

Streamed answers are cached too: they are assembled as they pass through and replayed as a fast stream later.

5.4 Request coalescing

Only requests that could be cached are coalesced, and only within one key. Each caller is billed for the tokens it received. If two or more callers shared an answer, it is clearly popular, so it is cached straight away.

5.5 Fair queuing

A model can only work on a few requests at once (its slots). Normally the model server queues the rest first come, first served, so one script sending 100 requests makes everyone else wait behind all of them. Tollgate takes that decision away from the model server: it never sends more than the slot count and keeps the waiting line itself.

This follows the published method Fairness in Serving Large Language Models (Sheng et al., OSDI 2024).

5.6 Streaming

Answers can stream word by word (Server-Sent Events). Tollgate relays the stream unchanged, counts tokens as they pass, and still bills correctly if the client disconnects. If the model breaks mid-answer, the client receives an error event and the failure is logged and counted.

5.7 Terse mode

The smart-terse alias adds an instruction to answer as briefly as possible. In one test it produced 85% fewer output tokens for the same question.

5.8 Logging and analytics

Each log entry records the key, alias, model used, tokens, latency, status, cache outcome, whether it was shared, how long it waited for a slot, time to first token, and any cost tags sent with the request.

7. Accounts and security

  • Keys are random 190-bit secrets stored only as hashes. Unknown keys are briefly remembered as invalid, so random guesses can't overload the database.
  • The admin token is generated automatically on first start and never sent to a browser. The dashboard uses it from its own server. The gateway refuses the public placeholder token in production.
  • Without Clerk, the dashboard has no sign-in, so it only answers on localhost. That also blocks a trick called DNS rebinding. The API and dashboard can be exposed separately, so sharing the API never exposes the dashboard.
  • With Clerk, each user sees only their own keys, logs and usage, and per-user caps protect the shared model budget. If Clerk keys are added without rebuilding the dashboard, it refuses to run rather than opening up.
  • The shared cache pool is opt-in: response timing could reveal that someone else asked the same thing, so cache headers are hidden there and it is off by default.

10. Observing it

  • Response headers on every answer: x-tollgate-model, x-tollgate-cache, x-tollgate-coalesce, x-tollgate-fallback, x-tollgate-queue-wait-ms, x-ratelimit-* and x-request-id.
  • Prometheus metrics at /metrics (with the admin token): token usage, request duration, time to first token, cache outcomes, coalesced requests, queue depth and queue wait. Names follow the OpenTelemetry GenAI conventions.
  • Logs are JSON lines, each carrying the request id, and every request is stored in the database.
  • Health: /health/live says the process is up; /health checks Redis, the database and the model provider, and drives the status light in the dashboard sidebar.

Cost tags: apps can send x-tollgate-tags: feature=search,team=growth; the logs can then be filtered by tag.

14. Known limits and future work

  • One gateway process. Coalescing and the fair queue live in the process's memory, so run a single gateway process. Sharing them across several instances (through Redis) is future work.
  • No migration tool. Schema changes are small additive steps applied at start-up; larger changes would need a proper tool such as Alembic.
  • Per-key priority weights are supported by the scheduler but not yet exposed in the dashboard.
  • Insert budgets need tuning against real traffic (see the benchmark note).
  • Not yet built: continuous integration, prebuilt container images, and a semantic (meaning-based) cache.
